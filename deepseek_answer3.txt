1. click 应该回传什么结构？最少几个字段？

最少 6 个字段，但核心结论是：不要把 click 设计成返回“成功/失败”的二值，要返回一个“副作用证据包”（side-effect evidence bundle），让 agent 自己做判断。

{

    "hit_report": {                        # 第一层：坐标上到底是什么
        "target_ref": "e12",
        "top_element_ref": "e12",          # elementFromPoint 实际命中
        "blocked": False,

    "effects": {                           # 第二层：发生了哪些可观测变化

        "dom_mutated": True,               # MutationObserver 摘要
        "mutation_summary": "added 3 nodes, removed 1",
        "active_element_changed": True,
        "focus_changed_to": "input#search"
    },
    "settled": True,                       # 是否在静默窗口内稳定
    "elapsed_ms": 87,
    "verdict": "observable_change"         # 机器可读的结论
}

verdict 的枚举值是 agent 决策的关键，建议至少四种：

verdict	agent 应该做什么
"observable_change"	信任副作用，继续下一步；但不保证是目标副作用，agent 可能需要 re-observe 确认
"no_observable_change"	不要假设成功；agent 应决定 retry、换 ref、或检查 overlay
"blocked"	不要 retry 同一个 ref；先处理 blocker（dismiss_blocker）
"dispatched_but_unconfirmed"	事件发出了但没有任何副作用证据；agent 应 re-observe 或换策略

为什么最少需要这 6 个字段：dispatched 回答“事件有没有到达”，hit_report 回答“到达的是不是目标”，effects 回答“页面有没有反应”，settled 回答“反应是否已经稳定”，verdict 把以上合成 agent 可直接消费的离散值。缺任何一个，agent 都要自己做推断，而 agent 不应该做这种推断——它应该拿到结构化证据，而不是一个它无法验证的“success: true”。

有实现明确指出：a successful upstream click is not proof that the web app handled the event or changed state。因此你的 click 返回结构必须把“派发成功”和“应用已响应”显式分开，而不是合并成一个布尔值。-

2. app-ready 的信号，network idle 不可靠，等什么？

结论：等 DOM mutation 静默，不要等网络。 network idle 在长连接、WebSocket、analytics 持续请求的场景下是结构性不可靠的，因为它的前提（“请求会停下来”）在你的目标页面上不成立。

可实现的判准，按优先级：

第一优先：MutationObserver + 静默窗口。 在 click 或 navigate 完成后注入一个 MutationObserver，监听 childList、subtree、attributes、characterData。当连续 idle_window 毫秒（建议 200–400ms，视页面复杂度）没有新的 mutation 时，认为 DOM 稳定。这正是 wait-dom-stable 的核心机制：监听 DOM 变化，有变化就重置计时器，idleTime 内没有新变化则认为渲染完成。关键陷阱：如果页面有持续动画或轮播，MutationObserver 可能永远不静默；此时需要加上“无关键区域变化”或最大超时兜底。-
31

第二优先：框架特定的 hydration marker（如果页面提供）。 部分 SPA 在 hydration 完成后会在 DOM 上留下可探测的标记，例如 document.querySelector('#app').__vue_app__ 存在、React 的 root 元素有 _reactRootContainer、或框架调用了 performance.mark('hydration-complete')。这些不是通用的，但如果你知道目标站点的框架，这是最精确的信号。可参考的做法是等待特定 DOM 元素稳定后再操作，而不是依赖 window.onload 或 DOMContentLoaded，因为 SPA 的内容是在这些事件之后才通过 JavaScript 动态生成的。-
31

第三优先：requestAnimationFrame 双帧 + 微任务排空。 在评估脚本里用 await new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r))) 等待两帧，再 await Promise.resolve() 排空微任务。这能捕获“同一轮事件循环内同步完成的 DOM 更新”，但无法捕获异步 fetch 回来的数据渲染。只适合作为轻量快速路径，不能作为唯一的 app-ready 判准。

不要用的信号：networkidle0/networkidle2（结构性不可靠）、load 事件（SPA 的 app-ready 远晚于 load）、document.readyState === 'complete'（同上）。

3. flat session 下 nested iframe（含 OOPIF）怎么处理？

结论：OOPIF 必须为每个 OOPIF target 开独立的 session，没有更轻的协议层做法。但同进程 iframe 不需要额外 session，可以直接在当前 session 的 Runtime.evaluate 里用 frames[i].document 访问。

理由和可操作规则：

OOPIF（跨进程 iframe）与同进程 iframe 的协议行为不同。在进程内 iframe 中，CDP 命令可以直接发送；但在 OOPIF 中，命令必须携带 sessionId 才能路由到正确的目标。OOPIF 的 target 在导航时创建，导航离开时移除；嵌套 OOPIF 的 attach 已被 Chromium 的 auto-attach-sub-sub-frame.js 测试覆盖。-
6

操作方案：

在 browser session 上调用 Target.setAutoAttach({autoAttach: true, waitForDebuggerOnStart: false, flatten: true})。这会自动 attach 直接子级的 OOPIF target，并通过 Target.attachedToTarget 事件给你一个 sessionId。

setAutoAttach 不是递归的：它只 attach 直接子级。如果 OOPIF 内部还有嵌套 OOPIF，你需要在那个 OOPIF 的 session 上再次调用 Target.setAutoAttach，才能 attach 它的子级。Chromium 的 auto-attacher 实现也印证了这一点：它不会把 local root 的子节点加入自己的 queue，因为那些子节点由 local root 自己的 TargetAutoAttacher 处理。-
1

拿到 OOPIF 的 sessionId 后，在该 session 上独立执行 Runtime.evaluate 和 Input.dispatchMouseEvent。注意：OOPIF 内的几何坐标是相对于 iframe 自己的 viewport 的，不是主页面 viewport 的绝对坐标。你需要把 iframe 在主页面中的偏移量加到 OOPIF 内部坐标上，才能派发正确的鼠标事件；或者直接在 OOPIF session 上用 iframe 内部坐标派发。

你只需要读文字和点击，不需要拦截网络，所以 Target.setAutoAttach 的轻量模式完全够用，不需要 Fetch.enable 或 Network.enable。

一个已被验证的陷阱：OOPIF 内 click 触发的 dialog 可能 fire 在 OOPIF 自己的 session 上，也可能 fire 在顶层 page session 上，两者都应视为“属于这次操作”；只有其他 tab 的 session 上的 dialog 才应该被忽略。你的 event routing 需要把这两种情况都归到同一个操作上下文。

4. DOM.getDocument(pierce=true) vs DOMSnapshot.captureSnapshot，选哪个？

结论：用 DOMSnapshot.captureSnapshot，不要继续用 DOM.getDocument。 在“要几何坐标 + 要跨 shadow DOM”这两个前提下，DOMSnapshot.captureSnapshot 是协议层面明确推荐且能力更完整的方案，DOM.getDocument 已被标记为 deprecated。-

逐项对比：

维度	DOM.getDocument(pierce=true)	DOMSnapshot.captureSnapshot
Shadow DOM	pierce=true 会遍历 shadow root，但返回的是嵌套的 Node 树，shadow root 作为独立节点嵌在树里，flatten 需要你自己递归	返回扁平化数组，Shadow DOM 已被扁平化处理，iframe、template contents、imported documents 也包含在内-

几何坐标	不直接返回几何信息。你需要对每个节点单独调用 DOM.getContentQuads 或 DOM.getBoxModel；对于 sticky/fixed 元素，getContentQuads 可能返回空数组，需要 DOM.resolveNode + Runtime.callFunctionOn(getBoundingClientRect) 补——这正是你已经踩过的坑	直接返回 layout.bounds（每个节点的 bounding box），可选 includeDOMRects 返回 offset/client/scroll rects，以及 includePaintOrder 用于遮挡判断。boundingBox 是文档坐标，忽略滚动偏移；如果你需要视口坐标，减去 scrollX/scrollY 即可-
12

一次调用获取的信息量	树结构 + 节点 ID；几何要 N 次额外调用（N = 节点数）	树结构 + 几何 + 可选的计算样式白名单，一次调用全部拿到
节点引用	nodeId / backendNodeId，但 nodeId 在导航后可能失效	backendNodeId，与 DOM domain 的 backendNodeId 兼容，可用于后续 DOM.resolveNode
坐标精度陷阱	getContentQuads 对 fixed/sticky 不可靠	有已知的缩放不一致问题：某些情况下 bounds 会被缩放，需要用第一个元素的宽度与 viewport 宽度之比做归一化校准；此外曾有 boundingBox 不一致的 bug，text 的 box 可能完全落在 div 的 box 之外

为什么对你的 observe 特别重要：你目前的 observe 是 DOM.getDocument 拿全树后在 Python 里 flatten，然后对每个可交互元素单独拿几何。DOMSnapshot.captureSnapshot 可以把“拿树”和“拿几何”合并成一次 CDP 调用，且 shadow DOM 已经是扁平的，不需要你处理嵌套 shadow root 的递归。对于 1000+ 节点的页面，这能显著减少 round-trip 次数。

需要注意的取舍：DOMSnapshot.captureSnapshot 返回的 layout.bounds 是文档坐标，不是 viewport 坐标。你现在的 observe 回传的是 viewport 坐标（x/y），如果你切换到 DOMSnapshot，需要自己做 viewport_x = bounds.x - scrollX 的转换。另外，DOMSnapshot 的 backendNodeId 与 DOM.getDocument 的 backendNodeId 是同一套标识，所以你可以继续用 DOM.resolveNode 拿到 Runtime.RemoteObjectId 来做 Runtime.callFunctionOn，不影响你现有的 hit-test 和 sticky 补算逻辑。

一句话：DOM.getDocument 是“先拿树，再逐个问几何”，DOMSnapshot 是“一次拿全树 + 全几何 + 扁平 shadow”。在你的场景里，后者在调用次数和shadow DOM 处理上都更优，唯一需要额外做的是坐标系的归一化和文档坐标→视口坐标的转换。
